## What makes this sprint different

Every previous sprint built one side of a mechanism. This one closes a circuit.

`comment.created` has existed as a contract enum value since CONTRACT-002 and as a
directory since CLI-002. SERVER-008 shipped the queue that stores it, SERVER-009 the
jobs that log it, and every one of those was verified by **enqueuing events by hand** —
`server.queue.enqueue(...)` in a test, or a JSON file dropped into `pending/`. Nothing in
the product has ever produced one.

- **SERVER-006 is the only producer.** After it merges, `comment.created` is generated by
  a person (or an agent) writing a sentence, and SPEC §8's participation semantics — the
  whole "opt-in per comment" design — stop being prose.
- **CLI-004 is the only consumer path.** SPEC §7's agent loop reaches the queue solely
  through the `corpus` binary; `apps/cli` contains **zero** queue, lock, or job code today.

The sprint's centrepiece is therefore not either issue. It is the loop:

```
corpus queue idle                     → parks, zero output, zero tokens          (§7)
POST /api/threads {requestsAgent:true} → thread file + parent anchor + ONE commit (§6)
                                       → comment.created lands in pending/        (§8)
  → the parked idle returns within a second, non-destructively                    (§7)
corpus queue claim-all                → the event, now in in-progress/
corpus lock break / POST /api/locks   → the document is coordinated               (§7)
corpus job log <evt> "…"              → the console feed grows live               (§7)
POST /api/threads/:id/turns --agent   → the reply turn, agent: engaged
corpus queue complete <evt>           → processed/
POST /api/threads/:id/resolve         → later turns stop re-triggering            (§8)
```

with git, SSE and the projection observed at **every** hop. If that sequence runs on a
real `corpus init` workspace against a real server driven by the real installed binary,
Phase 2's thesis holds and AGENT-002 has something to stand on. If it does not, the two
issues passed their own tests and the product does not work.

Three things make this batch riskier than its size suggests, and all three are
adjudications, not code:

1. **Thread creation and the lock guard flatly contradict each other in shipped
   artifacts.** `apps/server/src/locks/guard.ts`'s header comment says thread creation is
   *exempt* from the parent's edit lock; `packages/contract`'s `createThread` route
   **declares `423`** and justifies it ("since anchoring mutates the parent"). One of the
   two is wrong and SERVER-006 is where the disagreement becomes behaviour. **Open
   Conflict 1.**
2. **Forms have no contract surface at all.** SERVER-006 carries an acceptance criterion,
   an edge case and a test-strategy line for `formAnswer` → `form.respond`. Neither
   `formAnswer` nor any producer of `form.respond` exists in `packages/contract`
   (grepped: zero hits outside the event-type enum). **Open Conflict 3.**
3. **`corpus queue idle --timeout` cannot be registered.** `--timeout` is a **global
   flag** (`registry/globals.ts`), and `registry/validate.ts` rejects any command flag
   that shadows one — at module load, before `main` runs. CLI-004's issue file names
   `--timeout` in five places. **Open Conflict 8.**

Read Open Conflicts 1–14 before writing a line of either issue.

### Runtime gotchas that will otherwise be misread as bugs

- **`corpus init` seeds a small corpus and makes one initial commit.** The baseline is
  **one `template`** (`note`), **three `view`s** (`inbox`, `open-threads`, `attention`),
  **two `skill`s** (`comment`, `orchestrate`), **zero `agent-def`s**, all `evergreen:
  true`. Every count assertion below — rows, files, commits, queue entries — is relative
  to that baseline. State the baseline in your log rather than assuming an empty database.
- **Mention targets at baseline: two skills, no subagents.** `/comment` and `/orchestrate`
  resolve out of the box (`name: comment` / `name: orchestrate`, `type: skill`).
  **`@<subagent>` has nothing to resolve against** — `.claude/agents/` ships empty, and no
  route creates documents outside `data/docs/`. To test a resolved `@<subagent>`, write a
  real `.claude/agents/<name>.md` on disk and let the **watcher** project it (it is in
  `WATCH_ROOTS`, ~3 s); that is a legitimate out-of-band edit, not a workaround.
- **`.gitkeep` files live inside `.corpus/queue/<status>/`.** Anything that counts or
  lists queue events counts **`evt_*.json` only**. This has bitten sprints 003, 004 and
  005 and is live again for every enqueue assertion here.
- **`.corpus/` is gitignored** except the queue skeleton. `seen.json`, lock files, job
  logs, the pidfile and `cache.db` **never** appear in a commit. TEST-51 depends on this.
- **`.corpus/seen.json` is not watched.** `WATCH_ROOTS` is `data`, `.claude/skills`,
  `.claude/skills-archived`, `.claude/agents`, `.corpus/queue`, `.corpus/locks`,
  `.corpus/jobs` — a bare file directly under `.corpus/` is absent, and
  `classifyWatchPath` has no case for it. Closing that is SERVER-006's AC (TEST-52).
- **`DEFAULT_IDLE_TIMEOUT_SECONDS === MAX_IDLE_TIMEOUT_SECONDS === 480`.** The server's
  maximum hold *is* the eight-minute rearm window. The "successive 60–90 s segments" in
  CLI-004's design is therefore a **single request** in the default case. See Open
  Conflict 9 — do not build a segmenting loop and then claim it was exercised.
- **`idle` answers `204` with no body on expiry** (not `200 {idle:true}`), and `200
  {events:[…]}` — an **array**, `min(1)` — when work exists. The 204 carries **no halted
  indicator**. Open Conflict 10.
- **The CLI client sends `x-corpus-author: agent` on every request** (`apps/cli/src/client.ts`,
  hardcoded `actor: "agent"`). `POST /api/locks/{docId}/break` is **user-only** and 403s
  an agent actor — so a naive `corpus lock break` **cannot ever succeed**. Open Conflict 11.
- **`QueueEventSchema` has no `status` field.** `complete`/`fail`/`abandon` return the
  event without saying which directory it is in, so the CLI **cannot** report "already
  completed" from the response. Open Conflict 12.
- **`SQUASH_IDLE_MS = 30_000`, and the amend matches on `Corpus-Doc` + `Corpus-Actor`
  trailers.** Two thread writes to the same thread by the same actor inside 30 s fold into
  one commit. Several assertions below say "exactly one new commit" *because of* this, and
  several say "two" *despite* it — read which is which.
- **`SELF_WRITE_TTL_MS = 2000`, matched on path *plus* content digest, registered
  *before* the bytes hit disk.** A thread write registered afterwards loses the race and
  surfaces as a spurious out-of-band reconciliation — which will look like an anchor bug
  and is not one.
- **`diff-match-patch`'s `Diff_Timeout` is 1 s.** Anchor reconciliation runs on parent
  saves, not on thread writes; a thread write that takes ~1 s means it went through the
  document body path by mistake.
- **`better-sqlite3` is a native module.** Its first install in a fresh worktree may
  rebuild against the local Node ABI; do not report that delay as a performance result.
- **Node is v25.2.1 locally; CI pins Node 22.** Global `EventSource` is behind a flag on
  this build — observe SSE with **`curl -N`**, not a Node `EventSource` client. Do not
  "fix" the runtime and do not report the flag as a defect.
- **`curl` line-buffers.** Use `curl -N` and drain the stream; a `curl` whose output you
  never read will look like "no frames arrived".
- **`out.emit()` writes only under `--json` and may be called exactly once**; `out.line()`
  is suppressed under `--json`; `out.write()` always reaches stdout. `claim-all`'s
  "one JSON line in both modes" needs `write`, not `emit`. Open Conflict 13.
- **jsdom's `localStorage` quirk** affects `apps/ui` only. No issue in this batch touches
  `apps/ui` or `packages/kit`.

## Open Conflicts — orchestrator decision required before implementation

Eighteen disagreements between the issue files, the shipped contract, the shipped code and
the spec, in rough order of blast radius. Each carries a recommendation; the orchestrator
adjudicates **before** the domain agents start, and each adjudication is written back into
the affected issue file(s).

### 1. The lock guard and thread creation contradict each other in shipped artifacts

`apps/server/src/locks/guard.ts`'s header comment (shipped, SERVER-009) states the
exemption as settled: *"Thread creation and turns (SERVER-006). Commenting is not
editing… the anchor entry that thread creation writes into the parent's frontmatter rides
that exemption."* The shipped contract says the opposite for creation: `createThread`
**declares `423`** and justifies it — *"`423` when the parent is held by the other party's
edit lock, since anchoring mutates the parent"* — and `deleteTurn` declares `423` too.
`appendTurn`, `resolveThread`, `reopenThread` and `markThreadSeen` declare **no 423 at
all**, which settles those four by itself.

**Recommendation: split it on whether the parent is actually written.**

- **Turn append, resolve, reopen, seen: never 423.** The contract declares no such
  response; the guard is not called. Commenting is not editing.
- **Standalone and whole-document creation: never 423.** Nothing in the parent is
  touched — there is no anchor entry to write — so the contract's own justification does
  not apply.
- **Anchored creation and any deletion cascade that removes an anchor entry: 423** when
  the *other* party holds the parent's lock. The parent's frontmatter is genuinely
  mutated, which is exactly what the guard exists for, and it makes the contract's
  declared 423 reachable rather than decorative.

This satisfies both artifacts' *intentions* — comments are never blocked, writes to a
locked document are — and it is the only reading under which the declared `423` is honest.
**Whichever way this goes, `guard.ts`'s header comment must be edited to match**; leaving a
shipped comment that contradicts shipped behaviour is the defect this sprint would
otherwise ship. **TEST-125 is written from this adjudication and an unstated answer fails.**

Note also: `createLockGuardMiddleware` **exists, is unit-tested, and is mounted nowhere** —
production wiring uses the `assertWritable` seam on `DocsWorkspace`. SERVER-006 should use
the **seam** (one call per verb, before any read or write, on the **parent's** id), not the
middleware, for consistency with every shipped write verb. If the middleware stays dead
after this issue, say so.

### 2. Thread mutation responses have nowhere to put §14's warnings

`warningsField` is shipped and spread into exactly three shapes, all documents:
`DocMutationResponse`, `UpdateDocResponse`, `DeleteDocResult`. `CreateThreadResponse`
(`{thread, anchorId, eventId}`), `AppendTurnResponse` (`{thread, turn, eventId}`),
`CaptureResult` (`{docId, threadId, eventId}`) and `DeleteTurnResult` have **none**.

Meanwhile SERVER-006's writes go through `runMutation`, which **already produces**
`MutationResult.warnings` — so the warnings will exist and be **discarded**. And the case
is sharper than SERVER-005's was: anchored thread creation writes the **parent document's**
frontmatter, so a hook rejection leaves the parent's anchors map uncommitted while the
person who just posted a comment is told nothing at all.

**Recommendation: file CONTRACT-006 and run it in this sprint, before SERVER-006 merges.**
Add `warnings: warningsField` to those four response shapes. No routes, no request bodies,
no status codes — structurally the same additive change CONTRACT-005's rider already made
and already proved safe against the inventory invariants. Reasons:

- §14 is currently *selectively* true — document writes warn, thread writes cannot — and
  both go through one pipeline. Deferring means revisiting every thread handler later.
- **UI-008 (thread view) is the consumer and it is Phase 3.** The field has to exist before
  its consumer, not after.
- The diff is four lines plus regeneration.

**Fold the `appended` honesty fix into the same issue.** `AppendLogResultSchema` is
`{eventId, appended: z.literal(true)}`, but SERVER-009 ships a **4 MiB file cap past which
further appends return 201 and write nothing** — the response asserts `appended: true` for

### 5. Does an explicit `requestsAgent: true` beat `status: resolved`?

§8 says a resolved thread stops re-triggering the agent; the contract's `resolveThread`
description repeats it. Neither says what an **explicit** request does in a resolved
thread. SERVER-006's design computes `requestsAgent` first and then checks resolution only
on the *engaged* branch — which, read literally, means an explicit `true` enqueues even
when resolved.

**Recommendation: an explicit request wins.** Resolution suppresses the *automatic*
re-trigger, which is what §8 describes ("unless the user marks the thread resolved") — it
is not a mute button on a person deliberately typing `@agent`. The alternative silently
swallows an explicit instruction, which is the worse failure. **TEST-42 asserts whichever
answer is given and requires it to be stated.**

### 6. `DELETE /api/threads/:id` does not exist — thread deletion is `DELETE /api/docs/:id`

SERVER-006's AC 10 names `DELETE /api/threads/:id`. There is no such route in the contract
(the full path inventory is 34 paths; `/api/threads/{id}` has **`get` only**). Threads are
documents and `DocIdParamSchema` uses `DocumentIdSchema`, which accepts `th_*` — so thread
deletion goes through **`DELETE /api/docs/{id}`**, a route **SERVER-005 already shipped**.

**Recommendation: SERVER-006 extends the shipped `deleteDoc` handler** with the thread
branch — unlink `data/threads/<id>.md` and, when `parent` and `anchor` are set, remove that
key from the parent's `anchors` map, all in one commit. Correct AC 10's prose. Two
consequences to state:

- **`DeleteDocResultSchema` has no `removedAnchor`.** The cascade cannot be reported on the
  wire; the client learns it by refetching the parent. That asymmetry with
  `DeleteTurnResultSchema` (which *does* carry `removedAnchor`) is a wart, and adding the
  field is a candidate rider on CONTRACT-006 — **recommend leaving it**, because the parent
  refetch is required anyway and a second reporting channel is surface with no consumer.
- **`deleteDoc`'s description promises the opposite cascade** for the non-thread case:
  deleting a *document* leaves its threads as **orphaned records**, not deleted. Both
  behaviours are correct and they are different branches; do not let one overwrite the
  other. TEST-59 tests the thread branch; SERVER-005's shipped tests cover the document
  branch and must not regress.

### 7. `GET /api/threads/{id}` cannot return what AC 12 asks for

AC 12 says the read returns turns as `(idx, author, ts, body)` plus "anchor context when
anchored". `TurnSchema` is `{author, ts, body}` — **no `idx`** — and `ThreadSchema` carries
`anchor` as an **id**, with no selector, range or resolution.

**Recommendation: the contract wins.** `idx` is the array index and adding it is redundant
surface; anchor context is `GET /api/docs/{parentId}`'s `ResolvedAnchor[]`, which already
carries `{anchorId, selector, threadId, threadStatus, range, orphaned}` and is the shape
UI-007 will consume. Correct AC 12's prose. **TEST-65 and TEST-66 are written from this.**

### 8. `corpus queue idle --timeout` cannot be registered

`--timeout` is a **global flag** (`registry/globals.ts`: number, valueName `ms`, default
`10000`, "how long to wait for the workspace server before reporting it unreachable"), and
`registry/validate.ts` rejects any command flag shadowing a global — at **module load**,
with `corpus queue idle flag "--timeout" shadows a global flag`. CLI-004's issue file uses
`--timeout` in five places. There is a second, independent facet: the global `--timeout`
becomes the **transport** timeout (`AbortSignal.timeout(timeoutMs)` on every request in
`client.ts`), so a 480-second long poll issued through the standard client would abort at
10 seconds.

**Recommendation: rename the parking-window flag to `--wait <seconds>`, and make the idle
request opt out of the global transport timeout.** `--wait` reads correctly for a parking
command, does not collide, and leaves the global `--timeout` meaning exactly what it means
everywhere else. The long-poll request passes its own `AbortSignal` — which `client.ts`
already honours (`init?.signal ?? AbortSignal.timeout(timeoutMs)`) — sized to the segment
plus a margin. **Both halves must be done; renaming the flag without fixing the transport
timeout produces a command that always aborts at ten seconds and looks like a server bug.**
Correct the issue file, and note that **AGENT-002's skill text will be written from
whatever name is chosen** — so choose once.

### 9. The segmenting poll loop has nothing to segment

CLI-004's design specifies "successive long-poll requests (per-request wait capped at the
server's maximum, e.g. 60–90 s) until the total window elapses". The shipped constants are
`DEFAULT_IDLE_TIMEOUT_SECONDS = 480` and `MAX_IDLE_TIMEOUT_SECONDS = 480` — the server's
maximum hold **is** the eight-minute rearm window. So in the default case the loop issues
exactly **one** request, and the "e.g. 60–90 s" figure is a guess that predates SERVER-008.

**Recommendation: implement the loop, but size the segment from the contract, not from a
literal.** Import `MAX_IDLE_TIMEOUT_SECONDS` and use `min(remaining, MAX)` as the segment.
The default window then issues one request; a `--wait 900` window issues two, and the
second is shorter. That keeps the loop honest and testable (TEST-85 exercises the >480 s
path deliberately) without pretending a segmentation that never happens. Do **not**
hard-code 60, 90, or 480.

Related: **`--wait 0`** cannot be sent — `IdleQuerySchema.timeout` is `min(1)`.
Recommendation: `--wait 0` issues exactly one request with `timeout=1` and returns whatever
it gets, documented in the registry as "a single non-blocking probe". State it in the log;
a silent `timeout=0` is a 400 and a silent skip-the-request is a lie.

### 10. The idle timeout carries no halted indicator

CLI-004's AC requires `--json` to distinguish `reason: "halted"` from `reason: "timeout"`.
The contract's expiry response is **`204` with no body**. There is no field to read.

**Recommendation: on the window expiring, issue one `GET /api/queue/status` and report
`reason: "halted"` when its `halted` is true, `"timeout"` otherwise.** One extra cheap
request per eight-minute window is negligible, it uses a shipped route, and it is honest —
the client genuinely does not know until it asks. The alternative (adding a body or a
header to the 204) is a CONTRACT change, and it should be **filed rather than improvised**
if the orchestrator prefers it. **TEST-88 is written from this.**

Note the related shape difference: idle's success is `{events: [...]}` — an **array**,
`min(1)` — not a single event. CLI-004's AC says "printing a minimal event summary (id,
type)". **Recommendation: human mode prints one `<id> <type>` line per event; `--json`
emits the `IdleResult` verbatim, and the timeout object under `--json` is the CLI's own
shape (it has no contract counterpart) and must therefore be documented in the registry
example.**

### 11. `corpus lock break` cannot succeed as the CLI is built

`apps/cli/src/client.ts` constructs the client with **`actor: "agent"` hardcoded** ("the
CLI is the agent's only interface"). `POST /api/locks/{docId}/break` is **user-only** and
403s an agent actor. So the verb SPEC §7 describes as *"the human escape hatch for a stuck
agent lock… a button on the banner (and `corpus lock break <docId>`)"* would return 403
every single time.

**Recommendation: `lock break` overrides the actor per call to `user`.**
`createCorpusClient`'s middleware already defers to a per-call `params.header` override
("A per-call `params.header` override has already been applied, so only fill in the default
when the caller said nothing"), so this is one parameter, not a client redesign. Justify it
in a comment: breaking a lock is definitionally a human action — an agent breaking its own
contention defeats the mechanism, which is exactly why the server refuses it. Do **not**
build the general `--from user|agent` flag here; that is CLI-003's, and CLI-004 needs
exactly one override.

**Second half — idempotence vs. 404.** CLI-004's AC says `lock break` and `lock reap` are
idempotent; sprint-005 Open Conflict 7c adjudicated **404** for break/release of an absent
lock, and that is shipped. **Recommendation: `lock break` maps the server's `not_found` to
a stated no-op and exits 0** (`{"docId":…,"broken":false}` under `--json`, "no lock held on
<id>" in human mode); every other error still exits 5. Rationale: the agent loop must not
crash on a duplicated call after a retry, and the 404 is indistinguishable from "already
broken", which is the outcome the caller wanted. The cost — a genuinely unknown docId also
exits 0 — is stated in the registry description. If the orchestrator prefers strictness,
exit 5 on 404 and CLI-004's idempotence AC is amended instead. **TEST-107 asserts whichever
answer is given.**

### 12. The transition verbs cannot report "already in that state"

CLI-004's AC: "already-in-that-state → reported, exit 0". Server-side, `transition()` **is**
idempotent (`if (from === to) return current.event;`) and returns 200 — but
`QueueEventSchema` has **no `status` field** (`{id, type, created, source, payload}`), so
the response is byte-identical whether the event moved or was already there. The CLI cannot
observe the distinction.

**Recommendation: print a uniform confirmation that does not claim a transition** — e.g.
`event <id> is complete` rather than `completed event <id>` — and exit 0 either way. Amend
the AC's wording. Do **not** infer the prior state from a second request (racy) and do
**not** add `status` to `QueueEvent` for a message (it is real surface with a real cost:
the field is the on-disk directory, and putting it on the wire invites clients to branch on
it). If the orchestrator wants the distinction, it is a CONTRACT issue, filed.

### 13. `claim-all`'s "one JSON line in both modes" fights the Output contract

`out.emit()` writes **only under `--json`** and may be called **exactly once**;
`out.line()` is suppressed under `--json`; `out.write()` always reaches stdout and its doc
comment says it is for help text ("help is not data").

**Recommendation: `claim-all` uses `out.emit(batch)` under `--json` and
`out.write(JSON.stringify(batch) + "\n")` otherwise**, with the reason spelled out in the
registry description so nobody "improves" it with a summary line. This command exists for
machine consumption and the batch **is** the payload; a human-readable variant would be a
different command. Update `write()`'s doc comment to name this second legitimate caller.
**TEST-92/93 pin it.**

### 14. `deferredEventId` is still unreachable, and SERVER-006 does not change that

Sprint-005 Open Conflict 8 kept `deferredEventId` off the wire and deferred the setter to
"SERVER-006/CLI-004, filed then". Nothing in **either** issue's ACs sets it: SERVER-006
writes threads, CLI-004 wraps `break` and `reap`, and `AcquireLockRequestSchema` is still
exactly `{ttl?}`.

**Recommendation: leave it deferred and stop naming this batch as its owner.** The setter
belongs to whoever *defers* an edit — the orchestrator's own loop (AGENT-002) via a lock
acquire that records what it was going to do. Re-point the deferral to **AGENT-002 + a
CONTRACT issue**, and keep sprint-005's substitute evidence (a real lock file with the
field, broken over HTTP) as the standing proof until then.

### 15. `queue status` versus `halt --status`

CLI-004's AC offers a choice: "`corpus queue status` (or `halt --status`) — pick one and
document it in the registry."

**Recommendation: `corpus queue status`.** It maps one-to-one onto the shipped
`GET /api/queue/status`, which returns halt state **and** the five per-status counts — so a
`--status` flag on `halt` would under-describe its own response. It is also what a reader
of `corpus queue --help` will look for. **TEST-103 is written from this.**

### 16. `reap-stale --older-than` has nothing to send

CLI-004's AC declares `--older-than <duration>`. `POST /api/queue/reap-stale`'s request is
`{headers: ActorHeaderSchema}` — no query, no body. The threshold is server-side
(`DEFAULT_STALE_AFTER_MS = 900_000`, configured at `createQueueService`).

**Recommendation: strike the flag** and document in the registry that the server owns the
staleness threshold. Adding it means a contract change plus a service parameter for an
operator knob nobody has asked for. Note a related wire gap while you are here:
`QueueService.reapStale()` returns `{reaped, failed}` — events pushed past
`DEFAULT_MAX_ATTEMPTS` into `failed/` — but `ReapStaleResultSchema` is `{reaped}` only, so
the CLI **cannot** report the give-ups. That is a real (small) honesty gap; recommend
noting it and filing it rather than inventing output for it. **TEST-104 is written from
this.**

### 17. Nothing can set `agent: engaged`, and §8's whole re-trigger rule depends on it

SERVER-006's design says "the agent itself sets `engaged` on reply, per §7", and SPEC §7's
comment skill says "Close the loop by setting `agent: engaged` on first reply". But:
`UpdateDocRequestSchema` is exactly `{title?, body?, tags?, status?, due?, reviewed?,
evergreen?}` — **no `agent`** — there is no thread-update route, and
`ThreadAgentSchema`'s own doc comment asserts `engaged` is "set by the agent's first
reply" without naming a mechanism. As shipped, a thread can reach `requested` and never
`engaged`, which makes TEST-38, TEST-39 and TEST-41 — the entire engaged half of §8 —
unreachable through the product.

**This is the one conflict with no good option, and the orchestrator must pick.** Three
coherent answers:

- **(a) The server sets it.** An agent-authored turn (`x-corpus-author: agent`) on a thread
  whose `agent` is `requested` flips it to `engaged`, in the same write. **Recommended.**
  It is mechanical, it matches "on first reply" exactly, it needs **no contract change**,
  and it removes a step the skill could forget — which is precisely the kind of guarantee
  §6 already makes for anchor reconciliation ("a mechanical guarantee of the write path,
  not a discipline anyone has to remember"). The cost: the agent can no longer post a
  one-off reply without engaging, which §8's design does not appear to want anyway.
- **(b) A contract rider on CONTRACT-006** adding `agent?: ThreadAgent` to the turn-append
  request, set explicitly by the agent. Honest and explicit, costs a contract change and a
  step the skill must not forget.
- **(c) Defer**, and record that the engaged branch is untestable this sprint. Not
  recommended: it strands three of the enqueue matrix's rows and leaves the sprint's
  centrepiece (TEST-121 steps 7, 10, 11) unverifiable.

**TEST-121 step 7 and TEST-37 are written from this adjudication and an unstated answer
fails.**
