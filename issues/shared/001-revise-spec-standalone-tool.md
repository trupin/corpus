## Summary
SPEC.md describes a repo-as-app system where the CLI writes files directly and the server watches. The project has pivoted (decisions recorded in CLAUDE.md, 2026-07-26): Corpus ships as an installable CLI tool, the server is the sole writer, the agent interacts only through the CLI, and the API is contract-first via `@hono/zod-openapi` with a generated client shared by UI and CLI. Revise SPEC.md so it is again the single source of truth, with no contradiction between spec and decisions.

## Acceptance Criteria
- [ ] §2/§3/§4 describe the tool/workspace split: installed tool (npm bin `corpus`; server + CLI + statically served pre-built UI) vs. `corpus init`-created workspace (`data/`, `.corpus/`, config, git, product agent skills).
- [ ] All write paths route through the server; CLI is specified as a thin typed-client wrapper with no direct file access; "files are source of truth" and git auto-commit (author attribution, audit trail) are preserved server-side; watcher's role reduced to out-of-band edit reconciliation.
- [ ] Queue section rewritten: `corpus queue idle` long-polls the server (same rearm semantics); claim/complete/fail/halt are API calls.
- [ ] New contract section: `packages/contract` zod-openapi route definitions, committed generated `openapi.json` with drift check, generated typed client consumed by UI and CLI.
- [ ] Tech stack updated: TS everywhere (CLI included — replaces "plain Node ESM .mjs"), Vitest replaces node test runner, monorepo layout matches CLAUDE.md's Repository Structure.
- [ ] Auth: localhost bind + bearer token generated by `corpus init`.
- [ ] Server lifecycle commands specified: `corpus server start|stop|status|logs` (daemonized, pidfile in `.corpus/`), idempotent start, CLI errors clearly when server is down.
- [ ] §15 milestones re-cut to match the new build order (contract → server → cli → ui → agent loop → plugins), each with an executable check.
