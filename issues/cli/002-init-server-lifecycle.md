## Summary
Give the installed tool its two operator-facing surfaces: `corpus init`, which materializes a **workspace** (document tree, runtime tree, config with a generated bearer token and port, a git repository with an initial commit, and the product agent's `.claude/` skills copied verbatim from the tool's bundled `assets/workspace/` template), and `corpus server start|stop|status|logs`, which manages the per-workspace server process as a detached daemon with a pidfile and logfile under `.corpus/`. Together these are the "day zero" path: install the tool, `corpus init`, `corpus server start`, open the board.

`corpus init` is the one and only place where the CLI writes to disk — it exists precisely to create the workspace the server will then own. Every command after it goes through the server.

## Acceptance Criteria
- [ ] `corpus init [path]` (default `.`) creates: `data/docs/` (including `data/docs/inbox/` and `data/docs/templates/`), `data/threads/`, and the `.corpus/` runtime tree (`queue/{pending,in-progress,processed,failed,abandoned}/`, `locks/`, `jobs/`, `attachments/`).
- [ ] `.corpus/config.json` is written with `{ version, port, token, dataDir }`: the token is 32 bytes of CSPRNG entropy (base64url), the port is a free port (default 8765, probing upward when taken). The file is mode `0600`.
- [ ] The workspace is a git repository: `git init` (default branch `main`), a `.gitignore` covering runtime state (`.corpus/cache.db*`, `.corpus/jobs/`, `.corpus/attachments/`, `.corpus/seen.json`, `.corpus/locks/`, `.corpus/HALT`, `.corpus/server.pid`, `.corpus/server.log`, `.corpus/config.json`), and one initial commit authored as `user` containing the tracked tree.
- [ ] The bundled `assets/workspace/` template is copied **verbatim** into the workspace — the product agent's `.claude/` skills (orchestrate, comment) and agent definitions, seed view documents, and document templates — resolved relative to the installed package, so it works from a global npm install as well as from the repo.
- [ ] `corpus init` refuses to clobber: if the target already contains `.corpus/config.json` (or a non-empty `data/`), it exits non-zero with "already a Corpus workspace" and changes nothing. `--force` is **not** provided.
- [ ] `corpus init` is atomic-ish: on any failure partway through, it removes what it created in a previously empty target and reports the underlying error (never leaves a half-workspace that `init` then refuses to fix).
- [ ] `corpus server start` daemonizes the server: detached spawn, stdio redirected to `.corpus/server.log`, `unref()`ed so the CLI exits immediately; writes `.corpus/server.pid` (`{ pid, port, startedAt, version }`); polls the health endpoint until ready (timeout ~15 s) and prints the URL, or fails with the last lines of the log.
- [ ] `corpus server start` is idempotent: already-running (live pid + healthy) → prints "already running on :<port> (pid N)" and exits 0.
- [ ] `corpus server stop` sends SIGTERM, waits for exit (up to 10 s), escalates to SIGKILL, removes the pidfile; not-running → says so and exits 0.
- [ ] `corpus server status` reports running/stopped, pid, port, health-check result, uptime, and server version; `--json` emits the same as one object. Exit 0 when running, non-zero when stopped (so scripts can gate on it).
- [ ] `corpus server logs` prints the tail of `.corpus/server.log` (`--lines/-n`, default 50) with `--follow/-f` streaming until interrupted (clean exit 0 on SIGINT).
- [ ] A stale pidfile (process gone, or pid reused by an unrelated process) is detected and cleaned rather than reported as "running".
- [ ] Two workspaces initialized on the same machine get different ports and different tokens and can run their servers simultaneously; commands run in each directory reach their own server.
- [ ] Vitest coverage for token/port generation, scaffold contents, clobber refusal, pidfile lifecycle, and stale-pid detection.

## Technical Design

- `apps/cli/src/registry/index.ts` — register the `init` command and the `server` topic
- `apps/cli/src/paths.ts` — workspace path constants (`.corpus/server.pid`, `.corpus/server.log`, …) and package-relative resolution of `assets/workspace/`
- `apps/cli/src/**/*.test.ts` — colocated Vitest specs
- `docs/cli.md` — regenerated

### Key Implementation Details
**Token & port.** `randomBytes(32).toString('base64url')` for the token. Port selection binds a throwaway `net.Server` on each candidate starting at 8765 to prove it is free; the chosen port goes into config. `--port <n>` overrides and fails loudly if the port is occupied.

**Template copy.** The installed package ships `assets/workspace/` as package files (`package.json` `files` entry). Resolve its location from `import.meta.url` (`new URL('../assets/workspace/', packageRoot)`) — never from cwd. Copy recursively with `fs.cp(src, dest, { recursive: true, errorOnExist: true })`, preserving contents byte-for-byte; do not template-substitute inside skill files (AGENT-001 owns that content). Dotfiles (`.claude/`) must be copied — verify the copy includes them.

**Init ordering.** Create directories → write config (0600) → copy template → `git init -b main` → write `.gitignore` → `git add -A && git commit` with author/committer forced to the `user` identity via `-c user.name=... -c user.email=...` env/flags so the workspace's audit trail is consistent regardless of the operator's global git config. Track a list of created paths; on failure, unwind it when the target directory started empty.

**Daemonization.** `spawn(process.execPath, [serverEntry], { detached: true, stdio: ['ignore', logFd, logFd], env: { ...process.env, CORPUS_WORKSPACE: root, CORPUS_PORT, CORPUS_TOKEN } })` then `child.unref()`. `serverEntry` is resolved from the installed `@corpus/server` package (`require.resolve`/`import.meta.resolve`), not a relative path, so a global install works. The log file is opened in append mode; a header line (`--- corpus server start <ISO> pid=<n> port=<n> ---`) delimits runs.

**Readiness.** After spawn, poll `GET /api/health` (unauthenticated or token-authenticated per SERVER-003) every 100 ms up to 15 s. On timeout: kill the child, print the last 20 log lines, exit non-zero — never leave the operator with a silent failure.

**Liveness.** `process.kill(pid, 0)` proves the pid exists; combine with a health check on the recorded port to guard against pid reuse. Treat "pid alive but health fails" as **unhealthy, running** in `status` (report it as such) and as a hard error in `start` (tell the operator to `corpus server stop` first).

**Multiple workspaces.** Nothing is global: pidfile, logfile, port, and token all live in the workspace's `.corpus/`. No user-level registry of workspaces — cwd resolution (CLI-001) is the only lookup mechanism.

### Edge Cases
- **Queue skeleton must survive a clone** _(AGENT-001 handoff, 2026-07-26)_: `corpus init` places a `.gitkeep` in each `.corpus/queue/` state directory — the template's gitignore rule (`.corpus/*` + `!.corpus/queue/` + `.corpus/queue/*/*.json`) is designed around them; see `docs/workspace-template.md`. Also note `data/docs/inbox/` and `data/threads/` are created on disk but stay untracked while empty (per spec only the queue skeleton survives a clone) — init recreates them when resolving a cloned workspace.
- `corpus init` into a directory that already has a `.git/` but no `.corpus/` → reuse the existing repo (do not re-init), still create the workspace and commit; say so in the output.
- Target path does not exist → create it (mkdir -p); target is a file → usage error.
- `git` binary absent → init fails with an actionable message before creating anything (probe `git --version` first).
- `.corpus/server.log` grows unbounded → out of scope here, but `logs` must tail without loading the whole file (read the trailing chunk).
- SIGINT during `server logs -f` → detach the watcher and exit 0.
- `server stop` when the pid belongs to a different process (reuse) → do not kill it; clean the pidfile and report "not running (stale pidfile removed)".
- The server dies immediately (port stolen between probe and spawn) → readiness poll fails; surface the log tail showing `EADDRINUSE`.
- Running `corpus init` inside an existing workspace's subdirectory → allowed (nested workspaces are the operator's call) but warn that the nearest ancestor rule (CLI-001) will now resolve to the inner one.

## Testing Strategy
Vitest in `apps/cli`, colocated, using real temp directories (`fs.mkdtemp`) — no filesystem mocking:
- `init/scaffold.test.ts` — full tree created; `.gitignore` contents; template files (including `.claude/`) present and byte-identical to the source; config parses against the CLI-001 Zod schema; config mode is `0600`.
- `init/index.test.ts` — token uniqueness across two inits; port differs when the first port is held by a listening socket; clobber refusal leaves the directory untouched; failure mid-way unwinds.
- `init/git.test.ts` — repo initialized, exactly one commit, author is the `user` identity, runtime paths untracked (`git status --porcelain` clean, `git check-ignore` on `.corpus/cache.db` and `.corpus/config.json` returns them).
- `server/daemon.test.ts` — pidfile write/read round-trip; stale-pid detection with a pid that has exited; health-poll timeout path against a socket that accepts but never responds.
- Lifecycle integration (still Vitest, still real): spawn a trivial real `node:http` server through the daemon helper, assert pidfile + liveness + stop + pidfile removal.

## E2E Verification Plan

### Verification Steps
1. Install the tool as a user would (`npm pack` + global install, or `npm link`) so `corpus` is on PATH; run every step through the real binary.
2. In an empty temp directory: `corpus init` → inspect the tree (`find . -type d`), `cat .corpus/config.json`, `ls -la .claude/skills/`, `git log --format='%an <%ae> %s'` → one commit, `user` author.
3. `corpus init` again in the same directory → refuses, exit non-zero, `git log` still shows one commit.
4. `corpus server start` → prints the URL; `curl -H "Authorization: Bearer $(jq -r .token .corpus/config.json)" http://127.0.0.1:<port>/api/health` → healthy. `cat .corpus/server.pid`, `ps -p <pid>` → alive. Confirm the CLI returned immediately (the server survives the shell that started it — verify with a fresh shell).
5. `corpus server start` again → "already running", exit 0, same pid.
6. `corpus server status` and `corpus server status --json | jq .` → running, correct pid/port/uptime.
7. `corpus server logs -n 20` → startup lines; `corpus server logs -f` in one terminal while hitting an endpoint in another → new lines stream; Ctrl-C → exit 0.
8. `corpus server stop` → process gone (`ps -p <pid>` empty), pidfile removed, `corpus server status` non-zero exit. `corpus server stop` again → "not running", exit 0.
9. Stale pidfile: start, `kill -9 <pid>` directly, then `corpus server status` → reports stopped and cleans the pidfile; `corpus server start` → starts cleanly.
10. Two workspaces: `corpus init` in `/tmp/wsA` and `/tmp/wsB` → different ports and tokens; start both; from each directory `corpus server status` reports its own pid/port; a request with wsA's token against wsB's port is rejected.
