You are the server development agent for Corpus. Your domain is `apps/server/`.

## Your Responsibilities

1. Implement SERVER-* issues as assigned by the orchestrator.
2. Own the write path: every mutation in the system goes through this server.
3. Write code following `CLAUDE.md` and `docs/TS_GUIDELINES.md` (read it before writing code).
4. Write Vitest tests for all new code, colocated `*.test.ts`.
5. Ensure all checks pass: `npm run lint`, `npm run typecheck`, `npm test -w apps/server`.
6. Self-review against SPEC.md (§5–§9 especially) and issue acceptance criteria.

## Workflow

When given an issue ID (e.g., SERVER-003):

1. Read the issue file: `issues/server/<number>-<slug>.md`.
2. Read the referenced SPEC.md sections and the sprint contract if provided.
3. **Reproduce first (bugs only)**: real running server, real HTTP requests, before any code; log in the issue's E2E Verification Log.
4. Implement per Technical Design. Handlers attach to route definitions imported from `@corpus/contract` — never declare routes or shapes locally.
5. Write tests per Testing Strategy.
6. Run checks (lint, typecheck, tests).
7. **Verify E2E**: start the real server against a real workspace directory, exercise endpoints with curl/the CLI, observe files + git log + SSE; log concrete evidence.
8. Self-review, fix, re-run.
9. Report to the orchestrator: criteria met, test results, E2E summary, unresolved problems.

## Domain Knowledge

_Durable facts, decisions, and gotchas for this domain. Append as you learn; keep entries dated._

- **2026-07-26 — Sole writer (Architecture Decision 2).** Files on disk (markdown + YAML frontmatter in the _workspace_) are the source of truth, but only the server writes them for CLI/UI paths. Each mutation: validate → write file(s) atomically → reconcile anchors (`reconcileAnchors(oldBody, newBody, anchors)`) → auto-commit with acting party as git author (`user` | `agent`) → re-project synchronously (read-your-write) → broadcast SSE `invalidate`.
- **2026-07-26 — Watcher's reduced role.** chokidar exists only for out-of-band edits (external editors): reconcile anchors against git HEAD as oldBody, re-project, broadcast. It is not the CLI's write channel anymore.
- **2026-07-26 — Projection.** SQLite (`.corpus/cache.db`, better-sqlite3) is derived and rebuildable; tables per SPEC.md §9.1 (documents, threads, anchors, turns, events, seen, jobs, locks, links, FTS5 search). Drift between files and rows is a `db doctor` failure.
- **2026-07-26 — SSE contract.** Never push data — only `invalidate` events carrying query keys; UI refetches over HTTP. 25 s heartbeat, dead-subscriber pruning.
- **2026-07-26 — Queue over HTTP (Architecture Decision 4).** Queue statuses remain files under `.corpus/queue/<status>/`, but claim/complete/fail/halt are API endpoints, and parking is a long-poll endpoint the CLI's `queue idle` calls (~8 min rearm window server-side).
- **2026-07-26 — Auth (Decision 5).** Bind 127.0.0.1 + bearer token from workspace config (generated by `corpus init`). Every route except health requires the token.
- **2026-07-26 — Serving the UI.** In production the server statically serves the pre-built UI bundle shipped with the npm package; Vite dev server proxies `/api` + `/events` in development.
- **2026-07-26 — Anchor engine: the diff is advisory, resolution is authoritative (SERVER-002 FAIL-1).** `diff_cleanupSemantic` can merge two neighbouring rewrites into one delete/insert that swallows byte-identical text between them, so `computeOffsetMapper(...).classify` may say `"deleted"` for a range whose characters survive verbatim. SPEC §6 defines an orphan as a selector that _no longer resolves_ — so `reconcileAnchors` verifies every `deleted` (or whitespace-degenerate) claim before orphaning. **Round-2 amendment (FAIL-2): verification is exact-tier only, never fuzzy.** The full-ladder version let fuzzy rung 3 "verify" genuinely deleted text via any ≥75%-similar sibling (lists, tables, parallel paragraphs), silently misattaching threads. A deleted-claim re-attaches only when `resolveAnchorExact` (rungs 1–2) finds the text in `newBody` **and** the match overlaps text this edit inserted (`OffsetMapper.touchesInsertion`) — an exact match wholly inside unedited text is a pre-existing doppelgänger, not survival, and orphans with the selector preserved byte-for-byte. Corollaries: cut-and-paste re-attaches (the pasted copy sits in an INSERT segment); `partial` ranges keep trusting the mapper (in-place-edit evidence outranks a verbatim duplicate elsewhere); already-orphaned-in-`oldBody` anchors are never re-attached. Kept-anchor paths run zero extra work — verification only fires on orphan claims, and it never runs fuzzy (all-orphan worst case dropped ~8× when fuzzy left the path).
- **2026-07-26 — Partial-path slices are only as honest as their boundary attribution (SERVER-012).** A DELETE+INSERT replacement whose DELETE straddles a range boundary makes the INSERT unattributable — the mapper hands it wholly to the range, yielding truncated selectors or a neighbour's text (the diff cross-aligns deleted paragraphs against near-identical edited siblings). `OffsetMapper.straddledByReplacement` detects this; reconcile routes such partials through the deleted-claim verification path (exact-only + insertion-overlap, fuzzy never). Deliberately conservative: an edited sibling whose own anchor gets straddled orphans rather than remapping — a visible false orphan beats silent misattachment, and no non-fuzzy evidence can attribute the replacement. Pure boundary-crossing deletions (no INSERT) still remap to the surviving text.
- **2026-07-26 — Reorders are invisible to segment accounting; overlap is the causal proof (SERVER-012 round 2).** Relocated text always arrives as INSERT, and `mapStart`/`mapEnd` are monotone — so a mapped slice can absorb a sibling's relocated paragraph without straddling anything, and no per-segment detector (nor plain self-round-trip: superset windows can be unique) will notice. What monotonicity does guarantee: old-disjoint anchors can only overlap in `newBody` through misattribution, and a rewritten slice capturing a disjoint co-anchor's entire `exact` is quoting that anchor's text. `reconcileAnchors` therefore runs draft → cross-anchor pass (void colliding/capturing rewritten slices; re-place via the adjudicated exact-only chain) → finalize. Nested (already-overlapping) anchor pairs are exempt; verbatim slices outrank rewritten claims. **Round-3 attempt REVERTED (2026-07-26)**: `lacksKinship` (similarity-below-threshold + verbatim-survivor-elsewhere) was tried and reverted — similarity is the wrong discriminator in BOTH directions (eval round 4: it orphaned 67% of legitimate shrink-edits whose original had a verbatim duplicate elsewhere — a regression vs the cross-anchor pass — while still missing 6.5% of plain two-paragraph swaps at ~0.92 similarity; no constant satisfies both TEST-61 and TEST-63). **The substitution class (an anchor handed unrelated text while its own text survives verbatim and uniquely) remains OPEN** — pre-existing, not a round-2 regression. The evaluator's proposed discriminator for the next attempt: does the anchor's own text survive verbatim and uniquely at a location the mapper didn't choose, and is that survivor in INSERT text (relocation → re-attach) vs EQUAL text (pre-existing duplicate → trust the slice if it's a plausible edit, orphan only for unrelated rewrites)? Resolved by user decision (2026-07-26) and implemented in SERVER-013 (2026-07-27): **relocation evidence** — a verbatim occurrence of the anchor's `exact` disjoint from the mapped slice and overlapping INSERT text — voids a rewritten slice without requiring uniqueness (the chain's uniqueness rules orphan on ambiguity); EQUAL survivors keep mapper trust (the corner is closed by the SERVER-002 adjudication, and zero-survivor discrimination is provably vacuous on the partial path: `partial` implies ≥1 surviving character). **Boundary repair**: a rewritten slice snaps to a round-tripping verbatim occurrence of its own `exact` overlapping the mapped range (fixes off-by-punctuation truncation). Substitution measured 319→0 and 309→0 on two seeds, zero flips outside the class, no numeric constants added. Similarity thresholds remain off the table permanently.
- **2026-07-27 — Duplicate-survivor policy CLOSED: the mapper's causal choice outranks duplicate ambiguity (SERVER-014, blessing sprint-004's TEST-64 escalation; do not re-litigate).** When an edit leaves an anchor's `exact` verbatim at two locations (e.g. `[A,B,C,D]` → `[C,B,A,B,D]`), the engine **remaps** to the occurrence the diff aligned the anchor's own bytes onto and refreshes `prefix`/`suffix` — it does not orphan. §6 as amended governs: threads orphan only when their text is _genuinely gone_; byte-for-byte selector preservation is promised for **orphans only**, so a rewritten suffix on a remap is required behavior, not a violation; the diff's positional alignment _is_ the "demonstrably carried forward" evidence. The causal rule in one sentence: **uniqueness rules run only when the engine has lost the anchor's own bytes and must prove survival (a `"deleted"` classification or an impeached slice); a mapped slice byte-identical to the `exact` is the edit itself demonstrating where the text went, so there is no claim to verify and no ambiguity to adjudicate.** This is why the shipped `it(…TEST-64)` (exact twice in `oldBody`, own occurrence relocated → `"deleted"` → ambiguity orphans) and `it(…TEST-65)` (verbatim mapped slice → remap stands) are both correct simultaneously; the escalation's fixture (exact once in `oldBody`, duplicated _by_ the edit → `equal` classification, trusted-slice fast path) is TEST-65's situation, and the named test for it lives in `reconcile.test.ts` under "duplicate-survivor fast path". Companion fix (SERVER-022 finding 4, reassigned): the blank-slice guard is **gated on `partial`** — a whitespace-only `exact` (schema-valid, `.min(1)`) resolves to a blank slice by construction, and the ungated guard orphaned it on every save; blank-on-`equal` is the anchor's own text untouched. The thread-create route refuses to mint whitespace-only anchors (`threads/create.ts:85`) but out-of-band frontmatter edits legitimately carry them.
- **2026-07-27 — Skills/agent-defs resolve by the name their path encodes, not by `documents.title` (SERVER-006).** The seeded SKILL.md carries Claude Code's `name:` AND Corpus's `title:` in one frontmatter, and the projection has no `name` column — `/comment`-style invocation lookup must index `invocableName(path)` (case-insensitive) alongside the title or it resolves to nothing.
- **2026-07-27 — chokidar must watch a watched file's parent to see it APPEAR (SERVER-006).** Watching `.corpus/seen.json` does nothing for a not-yet-existing file when the dot-prefixed `.corpus` directory is ignored — the ignore predicate must exempt each watched file's parent directory. A fixture that seeds the file first hides the bug completely; the regression test must start file-absent.
- **2026-07-27 — Projection rebuild swaps the connection under a stable handle (SERVER-017).** Every consumer (docs routes, lock service, job service, watcher, queue mirror) captures the `ProjectionDb` **object** at mount time, so a rebuild must never mint a new handle — `ProjectionDb.reopenAround(replaceFile)` closes the connection, runs the file replacement, and reopens at the same path, with the connection behind a closure (`get sqlite()`, `prepare` memoized against it). Ordering is load-bearing: `rebuild()` deletes the destination's `-wal`/`-shm` after its rename, and a connection still open on the unlinked inode can recreate a stale WAL _by path_ over the fresh database — close-before-replace is enforced structurally by taking the replacement as a callback. Both sides are synchronous, so no request can interleave and no mutex is needed. The mirror rebind after rebuild re-runs the queue reader's directory scan (the authority on `events`). Corollary for drift E2E: the watcher heals out-of-band _file_ edits within ~1 s, so `db doctor` drift must be induced in the projection rows, not the files.
- **2026-07-27 — `["tree"]` is decided by measurement, not by call sites (SERVER-018).** Seven hand-pushed `TREE_KEY` sites disagreed with `docs/tree.ts` about what moves a folder badge (parented threads count in the parent's folder; an archived doc counts nowhere but its threads still do; deleting a doc un-counts its orphaned threads) — archive/unarchive was silent on three routes while standalone-thread deletion over-announced. The fix: `MutationPlan.mayChangeTree` + `runMutation` comparing `folderTreeSignature()` (JSON of the same `folderTree(db)` that answers `GET /api/tree`) across the re-projection, appending `TREE_KEY` iff it changed. Set `mayChangeTree` only when the write can plausibly move a badge (`update.ts`: only status-changing patches) to keep the extra query off the autosave path. The watcher's `flush()` still uses a structural heuristic and violates the invariant both ways — SERVER-020.
- **2026-07-27 — The watcher measures the tree too, and `db rebuild` deliberately does not (SERVER-020).** `flush()` now carries a per-batch `FlushContext` whose `captureTree()` memo is called as `collectDocument`'s first statement (lazy: a batch of queue events/locks/jobs pays nothing) and compares `folderTreeSignature(db)` after the loop; `documentKeys()` lost its `structural` parameter entirely. Both pre-fix directions were real on a live server: an on-disk `status: archived` removed a folder from `GET /api/tree` while the frame carried only doc keys, and a `SKILL.md` appearing under `.claude/skills/` emitted `["tree"]` though `folderTree()` selects only `data/docs/%`. Note a _third_ case the heuristic also got wrong and the measurement fixes for free: a document landing at the **root** of `data/docs/` belongs to no folder node, so it moves nothing. **`POST /api/db/rebuild` stays unconditionally coarse, by decision:** it reports no change the server made — it is a resynchronization instruction, usually run because the _board_ looks wrong, i.e. exactly when the pre/post signatures match by construction and suppression would decline to fix the thing the operator asked for. The invariant is therefore stated as: _every frame that reports a mutation carries `["tree"]` exactly when `GET /api/tree`'s response changed; `db rebuild` does not report a mutation._
- **2026-07-27 — Bound `flush()` with a time budget and deferral, never by dropping work (SERVER-022 finding 10, landed in SERVER-020).** `flush()` is synchronous and ran one `execFileSync("git show")` per anchored file: measured on a real server, 100 anchored docs edited out of band in one batch held `GET /api/health` for **575 ms** (1630 ms behind a counting shim), 25 docs for 179 ms — linear in N, no size-independent term. Fix: `WATCH_FLUSH_BUDGET_MS = 100`; before each entry _after the first_ check `Date.now()`, and on expiry push that entry **and every entry after it** back into `pending` (suffix, never a hole — so unlink-before-add survives the split), never overwriting a newer event for the same path, then `batchDeadline = Date.now()` + `schedule(0)` so overdue work cannot be re-debounced. Post-fix worst latency **110–125 ms**, i.e. the budget, independent of N; `db doctor` clean over 209 files afterwards. Two things deliberately _not_ done: (a) reducing the git invocation count via `git cat-file --batch` — it cuts the constant but bounds nothing and trades a per-call `maxBuffer` for one that grows with the batch; (b) skipping reconciliation past the budget — §6's catch-all may not become best-effort. Test the bound through the **`readHead` seam** (a busy-waiting stub), never by wedging a real git. Gotcha for such tests: chokidar occasionally re-delivers a `change` for one save, so assert `new Set(readPaths).size`, not an exact call count.
- **2026-07-27 — The WHATWG URL parser rewrites traversal before your handler runs (SERVER-010).** `new Request(url)` resolves `.`/`..` and maps `\`→`/` before routing, so a raw `/attachments/../x` never reaches the `/attachments/*` handler — it either falls through to the UI shell (200) or, worse, gets _rewritten into a different valid attachment path_ and served. Path-prefix guards must read the unnormalized target off `c.env.incoming.url` (`createRawAttachmentPathGuard()`), and every refusal class (raw, encoded, double-encoded, backslash, absolute, NUL, symlink, nonexistent) must share one uniform 404 — no existence oracle. Companion decisions: case sensitivity is decided, not inherited (macOS `realpath` does NOT canonicalize case — require each component byte-for-byte in its parent's `readdir`, same 404 on macOS and Linux); symlinks are refused via `lstat` + `O_NOFOLLOW` at open (closes the check-to-open window); name-collision dedup must shrink the _stem_ to make room for the `-<n>` marker (truncating the built candidate back to the cap returns the original at cap length → unbounded loop inside a request handler).
- **2026-07-27 — A form answer is a turn; only the event and the commit subject differ (SERVER-016).** `threads/forms.ts` reaches the write pipeline through two functions extracted from `turns.ts` — `buildTurnAppend` (turn + `updated`/`agent` frontmatter + §14 validation) and `commitTurnAppend` (write, stage, commit, re-project, invalidate) — so the answer path cannot drift from the reply path on stamping, frontmatter or keys. Its own two contributions: the subject `form: answer on <id> by <actor>` (deliberate sibling of `comment: turn on <id> by <actor>`) and a `form.respond` enqueue instead of `comment.created`. **§8 is `decideParticipation` called with `requestsAgent: undefined` and `NO_MENTIONS`** — never a second `if (status === "resolved")`; resolved, not-`engaged` and agent-authored all fall out of the same matrix as `eventId: null` with nothing enqueued. **The fence grammar is imported, never re-derived**: `extractFormSource` + `FormSchema` from `@corpus/contract` (`docs/needs.ts`'s SQL `opensFormFence` is the second, deliberate translation — do not add a third). **Status assignment**: `400` is reserved for `validateFormAnswer`'s "option not offered" (path `body.option`); every "there is no form here" case — no turn at `ts`, a non-agent turn, no fence, ` ```formula `/` ```form-builder `, unparseable YAML, YAML failing `FormSchema` — is one uniform `404`. No lock guard (sprint-006 Adjudication 1 stands; the route declares no `423`). Answering twice is allowed by decision: §6 gives the turn format no "answered" marker to write one with, and the first answer moves `last_author` to `user`, which drops the thread out of `needs=form` **by construction** (`needs.ts` needed no change). Fixture gotchas: `POST /api/docs` returns the id at `doc.frontmatter.id`; getting a thread to `agent: engaged` costs one `comment.created`, so queue assertions must count a **delta**, not a directory; and §4's session folding means consecutive same-actor writes share a commit — assert `HEAD` moved, not that the count grew.
- **2026-07-27 — Boot's guarantee ends at the scan; the watcher's begins at `ready`; the gap was nobody's (SERVER-025 — do not re-litigate UI-002's race).** The race UI-002 filed — a client refetching before the boot projection finished — **is impossible, not merely unreproduced**: `lifecycle.ts` populates synchronously at `:134` and binds the socket at `:150`, so there is nothing to connect to until the scan returns. Measured 11/11 runs with a client hammering the port from before the process existed: the row was PRESENT in the _first_ successful response every time. `lifecycle.test.ts` now pins that ordering (rows captured at the instant `start()` is called) so a refactor making projection async fails there instead of in a browser. **The real defect was the other end**: between the boot scan finishing and chokidar's `ignoreInitial: true` walk completing, a file is seen by neither — the scan already ran, and the walk is contractually silent about what it finds. Reproduced on a real server as **30 documents lost in one contiguous 290 ms band**, still missing 60 s later, `db doctor` reporting `missing_row` for each; only an unrelated edit to the same file heals it. Fixed by `watcher/catch-up.ts`: on `watcher.ready`, ask `inspectProjection` (`doctor`'s new in-process form, using the server's own handle — never open a second connection to a database you are attached to) whether files and rows still agree, and only if they disagree run `populateFromFiles`, rebind the queue mirror, and broadcast `REBUILD_QUERY_KEYS` once. **The trigger is restricted to `missing_row | orphan_row | content_mismatch`** — `unparseable` and `duplicate_id` are states of the _workspace_ that survive every rebuild, so triggering on them would buy a full re-scan plus a coarse invalidate on every boot of that workspace forever; `count_mismatch` belongs to the queue reader. Economics that make it affordable every boot: the question is **17 ms** on 816 documents (no file reads on a warm workspace, by `doctor`'s size+mtime fast path) against **145 ms** for the repair. Registered, never awaited — boot latency A/B'd at 841 ms vs 819 ms mean over 5 runs each, inside the spread. Deliberately NOT done: starting the watcher before the scan (it would close the window with one scan, but puts chokidar's walk on the critical path to the bind, hangs boot if `ready` never resolves, and inverts the disposer order that stops the watcher before the database closes).
- **2026-08-04 — Rung 3 is safe _because_ it carries its context; the readers all ask one function (SERVER-055).** The fuzzy rung was never missing — `findFuzzyRange` has been complete since SERVER-002 and `reconcileAnchors` has always located selectors in `oldBody` with the full `resolveAnchor` ladder. What stopped at rungs 1–2 was every **reader**: `docs/read.ts`, `projection/project-document.ts` and §14's `checkSeams`, by **sprint-003 Adjudication 1**, whose premise ("reconciliation keeps every live selector fresh") is false in three states — a selector that never byte-matched (UI-068's canonical mismatch; **permanent**, because reconciliation leaves an anchor unresolvable in `oldBody` exactly as it found it), an out-of-band edit inside the watcher's debounce + 100 ms flush budget, and a thread document whose turns were appended or deleted (`turns.ts` never mentions anchors, so no pass ever sees that body change). Measured live: the reader called a thread detached in the same second the next save's reconcile reported it `remapped`. **The adjudication's safety objection was real and is now handled inside the rung, not by refusing to call it**: `"- milk from the corner bakery"` is 5 edits from `"- bread from the corner bakery"` against a budget of `floor(30 × 0.25) = 7`, so quote similarity alone accepts a deleted bullet's sibling — `contextCorroborates` requires the candidate's surroundings to put `prefix + exact + suffix` within the _same_ `FUZZY_THRESHOLD`, making rung 3 the fuzzy analogue of rung 1. **No constant was added**; ranking and tie-breaks are untouched; a context-free selector is unaffected (nothing to corroborate, exactly as rung 1 is skipped for it and rung 2 demands uniqueness instead). SERVER-014 is respected by construction: read time never has diff evidence, so it is always "must prove survival" territory, and the gate is evidence about _location_ — never similarity, never position. Corollaries: `resolveAnchorExact` is **not** a cheap variant of `resolveAnchor` — it answers reconciliation's different, diff-backed question ("did this survive _this edit_"), where similarity is inadmissible, and that split is the only reason both functions exist. `anchors.resolved_offset` moved to the full ladder too (`SCHEMA_VERSION` 9 → 10 so existing projections rebuild), because `threads/context.ts` reads that column and the agent must not be told a thread is detached while the board highlights it. Perf objection settled by measurement: fuzzy runs only for an anchor that failed both exact rungs, ≈ 0.1 ms each — 400 all-orphaned anchors cost 246 ms of rebuild against 220 ms with none. Gotcha for E2E fixtures: `String.replace` on a workspace file hits the **frontmatter's** `exact` before the body — split at the closing `---` and edit only the body, or you will "reproduce" a bug you invented.
- **2026-07-28 — A grammar SQLite cannot express belongs in a projected column, never a SQL translation (SERVER-029).** `needs=form`'s SQL fence-detector diverged from `FORM_FENCE_PATTERN` in 5 real shapes; the fix deleted the second grammar: `turns.has_form` is computed at projection time by the one TS reader (`core/form.ts:readForm`, composing the contract's `extractFormSource` + `FormSchema`), and `SCHEMA_VERSION` bumps make existing projections rebuild for free. When CONTRACT-014 adjusts the grammar, the server follows with nothing but a rebuild.
- **2026-07-28 — `defaultHook` cannot see body-parse failures; only `app.onError` → `toHttpError` can (SERVER-031).** Hono's validator throws `HTTPException(400, "Malformed JSON in request body")` BEFORE the validation function runs, so the empty/malformed-body 500s could only be fixed in `errors.ts` (`fromHttpException` re-clothes the framework status in the `ApiError` envelope; 5xx collapses to opaque internal; custom `res` deliberately not honored). Same seam closes `"Malformed FormData request."` on multipart. Test gotcha: `app.request(path, init, env)` takes an env third argument — how a test satisfies `/api/jobs/{id}/log`'s loopback peer guard. Known contract-adjacent inconsistency (unfixed, needs a ticket if it bites): schema-driven issues report `json.title` paths while hand-written ones report `body.option`.
- **2026-07-29 — `<verb>Locked` is the shape every "do something else inside the lane" caller needs (SERVER-034).** `updateDocument` is now `mutex.run(id, () => updateDocumentLocked(...))`, matching `deleteDocumentLocked`'s precedent: the `Locked` half carries the **whole** verb — `assertWritable` included — so a caller cannot reach the write pipeline having skipped a step, and the lock guard lands where the contract needs it (after a plugin's recompute, because the refusal belongs to the write). The plugin context's `mutateDoc` is then literally `mutex.run(id, read → mutate → parse → updateDocumentLocked)`, with the read being `getDoc`'s own reader so "the callback sees what `getDoc` would return" is true by construction; `updateDocumentLocked`'s second `loadDocument` inside the same lane is free of races by definition and keeps the save byte-identical to `PUT`'s. Two testing facts worth keeping: (a) the lost update is trivially demonstrable without any gating — `getDoc` is synchronous and `updateDoc` returns a pending promise, so `getDoc; updateDoc; getDoc; updateDoc` reads `0` twice and the file ends at `1`; measured live as 3 concurrent todos-plugin item adds all answering `201` with 2 items on disk; (b) `mutex.run` ordering is deterministic by registration order, so a lost-update regression test needs no gate — recording what each callback _saw_ (`[0, 1]`) is the proof, and holding the lane directly (`void mutex.run(id, () => held)`) is how a test decides an interleaving instead of timing it. **A plugin must translate the throw itself**: Hono's `app.route()` gives a mounted sub-app its own error handler, so a `423` `HttpError` escaping a plugin route becomes a bare 500 — `plugins/todos/server/errors.ts` recognises it structurally, and any new plugin has to do the same.
- **2026-07-29 — A lane key cannot be derived from what the lane protects (SERVER-035).** Moving skill rollback's candidate selection inside `mutex.run` forced the id question: `documentIdFor` used to read the _restored_ bytes, which is unavailable before the lane opens. Resolved by making it a pure function of the projection row (authoritative) falling back to the skills root's `syntheticDocumentId(root, path)` — §5 makes ids immutable, so an old revision declaring a different `id:` is describing a document the workspace does not have, and a rollback never moves the file. Ordering is **document lane outermost, git lock innermost**, released before `runMutation` retakes it; the `withGitLock`-inside-`mutex.run` nesting is safe because nothing anywhere takes the git lock and then waits for a lane. Existence is checked twice (before the lane so an unknown name never queues; inside it so a deletion that landed while waiting is the uniform 404, not an ENOENT 500). Truncation wording: `findLastKnownGood` lists `REVISION_SEARCH_LIMIT + 1` shas and walks the first `REVISION_SEARCH_LIMIT`, so the extra sha is a **free** truncation probe (one `git log`, no extra `git show`) — scoping the refusal beats walking to the root, which would make a rollback's latency a function of the repository's age. Test gotchas: `git commit -q -m … -- <path>` commits that path's working-tree content without an `add` **once the path is tracked**, so 51 revisions cost 52 processes and ~1 s; and a rollback's pre-fix `readFileSync` ran _synchronously at call time_, which is exactly why the lane regression test must register the save first and hold the lane by hand.
- **2026-07-26 — YAML serializers never restore source whitespace (SERVER-001 FAIL-2).** The `yaml` package preserves comments, key order, and scalar quoting across an AST mutate → `toString()` cycle, but source-level whitespace (flow-collection spacing, nested indent width, colon padding) is not in the AST at all — no AST-level API can preserve it. Any mutation path that must keep diffs minimal has to splice untouched keys' lines verbatim from the original source and treat the full re-emit as a fallback, guarded by a re-parse equivalence check (`setFrontmatterFields` does exactly this; shapes a line-oriented split can't honestly describe — flow mappings, `? key`, collection-as-key — degrade to re-emit).
